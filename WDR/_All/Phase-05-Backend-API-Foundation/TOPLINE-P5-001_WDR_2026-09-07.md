## BACKEND MODULE ARCHITECTURE

Proposed structure:
- `common/responses/` — Standard response helpers
- `common/dto/` — Shared DTOs (future)
- `common/filters/` — Exception filters (future)
- `prisma/` — Global PrismaModule (exists)
- `health/` — Health module (refine existing)
- `tenants/` — Tenant read service (future)
- `audit/` — Audit logging service (future)

## SERVICE LAYER RULES

- Controllers handle HTTP boundary only
- Services contain business/read logic
- PrismaService used only in services/repositories
- No raw DB access in controllers
- No cross-tenant query without tenant filter
- No direct exposure of internal Prisma objects
- Responses mapped to safe DTOs

## PRISMA ACCESS RULES

- PrismaService used only in services/repositories
- Controllers never access Prisma directly
- No raw Prisma errors returned to client
- Services catch and transform errors
- PrismaService onModuleInit remains empty until DB health check implemented

## TENANT ISOLATION PLAN

- Vendor, Category, Product carry tenantId
- All queries filter by tenantId for tenant-scoped data
- User is global (platform-level)
- Membership bridges User ↔ Tenant
- AuditLog includes tenantId where applicable
- Owner/Admin cross-tenant access requires explicit authorization (future)

## API RESPONSE STANDARD

Success: `{ ok: true, data: {}, meta: {} }`
Error: `{ ok: false, error: { code: "", message: "" } }`

No sensitive stack traces. No raw Prisma errors. Predictable status codes.

## ERROR HANDLING PLAN

- Safe error responses — no sensitive details
- Predictable status codes (400, 404, 409, 500)
- Centralized exception filter (future)
- Logging without secrets

## DTO/VALIDATION PLAN

- Read-only response DTOs first
- No package installation in P5-001
- Validation pipes deferred
- class-validator/class-transformer considered later

## AUDIT LOGGING PLAN

- AuditLog model exists
- Audit write service introduced later
- No audit logging in first API task unless explicitly scoped
- No fake audit claims

## DEFERRED API DOMAINS

Auth/RBAC, user registration, vendor onboarding, product CRUD, category CRUD, cart, orders, checkout, payments, RFQ, subscriptions, CRM/ERP modules, admin destructive operations.

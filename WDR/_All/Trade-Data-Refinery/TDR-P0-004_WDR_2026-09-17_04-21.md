## 5. Decisions Recorded (ADR-TDR-003 to ADR-TDR-012)

### ADR-TDR-003 — Canonical MVP Record Type

**Status:** `CLOSED`

**Decision:** The canonical MVP record is a **product-linked trade line**, not a full document suite. Each canonical record links to a platform Product entity, carries tenant scope, and represents one normalized row from an approved source with full lineage back to the source batch, row index, and rule versions applied.

**Rationale:** The roadmap explicitly states "product-linked trade line, not a full document suite" as the recommended MVP scope (Section 20). A full document suite (with header, line, and attachment sub-records) exceeds MVP scope and cannot be safely contracted before the schema work in TDR-P3-001. A product-linked trade line aligns with the existing platform product domain, minimizes new migration surface, and is the narrowest viable canonical model for the approved vertical slice.

**Rejected:** Full document model (over-scoped for MVP), headless trade line with no platform link (cannot enforce tenant/product isolation), generic key-value store (untestable and ungovernable).

**Trigger to change:** PM approval required to expand the canonical model beyond a product-linked trade line.

**Required by:** TDR-P3-001

### ADR-TDR-005 — Synchronous vs Durable Job Processing

**Status:** `CLOSED`

**Decision:** For the MVP, TDR ingestion processing runs **synchronous in-process** (request-scoped NestJS service calls, no queue, no worker process). Durable queue-based processing (BullMQ, SQS, Temporal, or similar) is **deferred** pending load evidence.

**Rationale:** The roadmap explicitly states "start with the simplest measured safe option; do not authorize queues or orchestration." In-process synchronous processing: (a) has no additional infrastructure dependency, (b) is testable with existing Jest setup, (c) produces clear stack traces on failure, (d) is reversible — adding a queue later is a bounded task, removing one is disruptive. A queue must not be adopted before ADR-TDR-011 establishes the file limits within which synchronous processing is safe.

**Constraint:** If load testing in TDR-P4-003 shows that synchronous processing cannot meet the approved limits, the durable queue decision reopens as a separate ADR requiring PM authorization.

**Rejected:** BullMQ at MVP (premature complexity), database-polling worker (fragile), Temporal (unproven in this stack, major infrastructure dependency).

**Required by:** TDR-P4-002

### ADR-TDR-006 — Duplicate Identity and Conflict Policy

**Status:** `CLOSED`

**Decision:**
1. **Exact duplicate** (same `source_id`, same `supplier_code`+`product_sku`, same batch): silently suppressed; not published; counts recorded in reconciliation.
2. **Cross-batch conflict** (same identity key, different values across batches): **quarantined** for human review; not autonomously resolved; reviewer must approve, reject, or return for source correction.
3. **Identity key:** composite of `supplier_code` + `product_sku` within a tenant scope. `source_id` serves as the within-file deduplication key.

**Rationale:** Exact duplicate suppression preserves idempotency (safe replay). Conflict quarantine prevents autonomous overwrite of canonical data without traceable approval (aligns with roadmap data integrity invariants). The composite key is the minimal identity that can be verified against platform product data without creating a dependency on a stable external ID.

**Invariant:** No canonical record may be overwritten without an attributable human approval and a prior-value audit trail.

**Required by:** TDR-P3-002

---

### ADR-TDR-007 — Automatic Normalization Boundaries

**Status:** `CLOSED`

**Decision:** Automatic normalization is **strictly limited to deterministic non-material formatting corrections**. The following are permitted automatically:
- Trim leading/trailing whitespace from string fields
- Normalize date strings to YYYY-MM-DD (if unambiguous)
- Normalize boolean strings (`"true"`/`"1"`/`"yes"` → `true`, `"false"`/`"0"`/`"no"` → `false`)
- Uppercase ISO codes (currency, country, unit of measure) when the value matches a valid code case-insensitively

The following require explicit human review and approval and **must not be automated**:
- Any numeric field correction (unit_price, quantity_available)
- Mapping an unknown unit_of_measure or currency to a known code
- Filling a required field from a default or heuristic
- Any correction where the normalized value differs from the raw value in a way that changes meaning

**Rationale:** Autonomous material correction creates unmeasurable data liability. Deterministic formatting is reversible and auditable. The boundary aligns with the roadmap's "deterministic non-material formatting only" requirement and ensures that all material differences between raw and canonical records have an attributable human decision.

**Required by:** TDR-P3-002

---

### ADR-TDR-008 — Review Separation of Duties

**Status:** `CLOSED`

**Decision:** Material corrections (any change to a numeric, identity, or required field beyond automatic normalization) require a **distinct approver** — the actor who submits a correction cannot be the actor who approves it, where technically feasible within the tenant's membership. Where a tenant has only one eligible reviewer (no separation is technically possible), the system must record a `SINGLE_REVIEWER_EXCEPTION` reason and flag the record for PM/owner awareness.

**Permissions model (provisional):**
- `tdr.view` — read batch results and lineage
- `tdr.quarantine.review` — approve/reject/return quarantined records
- `tdr.correction.submit` — submit a material correction proposal
- `tdr.correction.approve` — approve a correction proposal (must not be the submitter)

**Rationale:** Separation of duties is a standard financial/trade data control. It prevents a single actor from both proposing and approving a change to canonical trade data. The `SINGLE_REVIEWER_EXCEPTION` path ensures the system is not blocked in small tenants while still recording the control gap for audit.

**Required by:** TDR-P5-002

### ADR-TDR-010 — Marketplace/ERP Integration Boundary

**Status:** `CLOSED`

**Decision:** TDR integration with the ToplineShop marketplace and any ERP system is **contract-only and disabled by default**. This means:
- Accepted canonical trade line records are **not** automatically published to the marketplace product catalog.
- ERP connectors (any external system pushing or pulling TDR data) are **not** implemented in the MVP.
- The integration boundary is a **typed internal service contract** (TypeScript interface), not a live API or event emitter at MVP.
- Activation of marketplace publication requires a separate PM-authorized bounded task.
- ERP connectors require separate PM authorization and scope definition.

**Rationale:** Automatic marketplace publication from a trade data batch bypasses the existing product governance and tenant safety controls. The contract-only boundary keeps the dependency explicit and testable without coupling TDR to marketplace release cycles. Any live integration introduces cross-module regression risk that must be separately gated.

**Required by:** TDR-P6-004

## 5. Audit Scope and Findings

### 5.1 Frontend coverage

The TDR frontend does include a broad preview surface for:

- route shell and overview;
- mock metrics;
- batch filtering/search/pagination;
- batch detail modal;
- project management panel;
- quarantine review modal;
- source configuration modal;
- import workflow modal.

This is a solid preview system, but it remains a static mock layer, not a freeze-certifiable production frontend.

### 5.2 Roadmap vs. registry truthfulness

The approved roadmap defines the frontend sequence as a freeze audit around the end of the TDR preview sequence. The actual executed registry tasks include multiple preview tasks but not the required freeze audit.

The registry currently contains:

- `TDR-P1-006` = source configuration preview;
- `TDR-P1-007` = import workflow preview;
- no `TDR-P1-008` freeze audit executed;
- no G1 pass declaration.

This creates a governance gap: the freeze gate is still unproven even though the UI has many preview screens.

### 5.3 Hard-coded values in `TdrProjectManagementPanel.tsx`

`src/components/tdr/TdrProjectManagementPanel.tsx` contains hard-coded governance values, including:

- `TASK_PROGRESS` array with static task states and titles
- `GOVERNANCE_GATES` values for G1/G2/G3/G4
- `RISKS` array with severity and detail text
- `WDR_ENTRIES` array with task IDs and local file paths
- summary values such as:
  - `Current TDR Phase` = `P1 — Frontend Proof`
  - `Completed TDR Tasks` = `6 of 7`
  - `Current Task` = `TDR-P1-004`
  - `Next Planned Task` = `TDR-P1-005 (Owner/PM to decide)`
  - `Frontend Gate G1` = `In progress — not frozen`
  - `Backend Gate G2` = `Blocked — not started`
  - `Backend Status` = `Not started`
  - `Last Accepted WDR` = `TDR-P1-003`
  - `Open Blockers` = `0`

These values must, in future, come from the canonical registry in `src/project/projectRegistry.ts` and must not remain hard-coded in a dashboard that is presented as truthful status evidence.

**Notable issue:** this file is not registry-driven and therefore does not satisfy the project’s “single source of truth” requirement.

## 6. Accessibility and UX Audit

### 6.1 Strong points

- route-level page structure is clear and readable;
- many buttons include `aria-label` values;
- modal dialogs use `role="dialog"` and `aria-modal="true"` in multiple panels;
- focus is moved to the close button when modal opens in several panels;
- several panels show visible explanatory note banners;
- keyboard Esc closes modals in several implementations;
- status styles combine color with text labels, which is acceptable for preview UI.

### 6.2 Missing or weak areas

- inconsistent live status truthfulness: some panels present static state as if it is current operational truth;
- `TdrProjectManagementPanel.tsx` is a hard-coded control panel, not a registry-backed dashboard, so its “status” claims are not authoritative;
- several controls are inert but visually resemble action buttons; this is acceptable only if clearly labeled as preview-only, which is mostly true but not uniform across all panels;
- the panel system does not yet provide a canonical evidence lineage view for the project dashboard;
- there is no visible workflow that shows “missing evidence” or “stale evidence” states in the UI;
- there is no full “lineage and quality-reporting workflow” in the user experience, which was called out in the roadmap as a required TDR capability.

### 6.3 Keyboard/focus review

Keyboard navigation is mostly acceptable for the preview panels, but the audit does not find a fully mature freeze-grade navigation model. The current UI is fit for static preview, not a declared production freeze gate.

## 8. Dashboard Truthfulness Findings

This is the primary blocker for a freeze declaration.

The TDR dashboard does not yet satisfy the project governance rule that the dashboard must derive from the canonical registry. The current dashboard is static and not registry-backed.

Concrete problems:

- the panel mixes static preview data with statements that look like operational status;
- it silently implies control truth where only mock data exists;
- it does not show the most recent evidence date and commit reference from the canonical registry;
- it does not clearly mark stale or missing evidence;
- it does not derive task status, progress, gates, risks, WDR references, or next action solely from the registry;
- it can mislead a viewer into treating mock governance status as real program status.

This is exactly the kind of issue that must be addressed in `TDR-P1-009` and cannot be silently accepted in this audit.

---

## 9. Missing Workflow Coverage

The TDR roadmap and the requirement list both call out missing or incomplete coverage around:

- lineage view;
- quality-reporting workflow;
- lifecycle evidence and audit lineage across source → batch → validation → publish;
- clear stale/missing evidence in the dashboard;
- registry-driven dashboard truthfulness.

The current TDR frontend delivers preview screens but not the full lineage and quality reporting workflow expected before freeze signoff.

### `TDR-P1-009 — Registry-Driven TDR Project Dashboard`

- derive task status, progress, gates, risks, WDR references, and next action from the canonical registry;
- show the latest evidence date and commit reference;
- clearly identify stale or missing evidence;
- remain frontend-only initially;
- never read repository WDR files directly in the browser;
- never create backend/database work solely for dashboard metrics.

This task is required for governance truthfulness, but it is explicitly out of scope for this audit and must not be implemented here.

---

## 11. Result

### Decision: BLOCKED

The TDR frontend preview is useful and visually mature, but it is not yet a valid freeze gate for backend work.

Reasons:

1. The roadmap and registry do not match on the intended freeze task sequence.
2. The actual freeze gate is not declared and cannot be declared from the current evidence.
3. The project management dashboard is hard-coded rather than registry-driven.
4. Missing lineage and quality-reporting workflows remain unimplemented.
5. The dashboard can misrepresent operational truth as live project truth.

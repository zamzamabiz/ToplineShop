## IMPLEMENTATION

### `src/types/api.ts` (modified)

Added a new section after `ProductFilters` with five enum-like literal
union types and four request interfaces, mirroring each backend DTO 1:1:

```text
TenantType      = "PLATFORM" | "VENDOR"
TenantStatus    = "ACTIVE" | "SUSPENDED"
VendorStatus    = "DRAFT" | "ACTIVE" | "SUSPENDED"
CategoryStatus  = "ACTIVE" | "HIDDEN"
ProductStatus   = "DRAFT" | "ACTIVE" | "ARCHIVED"

CreateTenantRequest    { name; slug; type: TenantType; status: TenantStatus }
CreateVendorRequest    { tenantId; name; slug; status: VendorStatus;
                        description?; logo? }
CreateCategoryRequest  { tenantId; name; slug; status: CategoryStatus;
                        icon?; parentId?; sortOrder? }
CreateProductRequest   { tenantId; vendorId; categoryId; name; slug;
                        basePrice: number; status: ProductStatus;
                        description?; currency?; inStock? }
```

Design choices:
- **Literal string unions** for enum-like fields (e.g. `type: TenantType`)
  rather than `string`, so the TypeScript compiler catches typos at the
  call site before the request reaches the API. This is stricter than the
  existing `*Summary` response types (which use `string`), but is
  appropriate for **request** types whose values are sent to a closed
  set of backend enums; **response** types stay permissive so future
  backend enum additions don't break the frontend.
- **Optional fields use `?`** matching the backend DTOs. No defaults
  baked into the type — defaults (`currency: "NGN"`, `inStock: true`)
  live in the service layer, so the frontend type reflects what the
  backend will accept, not what the backend will assume.
- **`basePrice: number`** — JSON-decoded, finite, non-negative. The
  backend `class-validator` enforces the same constraints; the type
  here just tells the compiler "send a number".
- Existing types are **untouched** — `*Summary` / `*Detail` /
  `ProductFilters` / `Api*` / response/error helpers all byte-identical
  to the pre-P7-009 state.

### `src/lib/api-client.ts` (modified)

Added one new helper and four new client methods, preserved all 11
existing GET methods byte-for-byte.

New helper `postApi<TRequest, TResponse>(endpoint, data)`:
- `POST` to `${API_BASE_URL}${endpoint}` with `Content-Type:
  application/json` header and `JSON.stringify(data)` body.
- Same response-shape handling as `fetchApi`:
  - non-`ok` HTTP response → throw `ApiError` with
    `code: "HTTP_<status>"` and `status: <status>`
  - body with `ok: false` → throw the body.error as `ApiError`
  - body with `ok: true` → return as `ApiResponse<TResponse>`
- Same catch block as `fetchApi`: re-throws existing `ApiError`s, wraps
  everything else as `ApiError` with `code: "NETWORK_ERROR"`.
- Generics `<TRequest, TResponse>` keep the call sites strictly typed:
  the compiler enforces the request payload shape and the response
  envelope.

New methods on the `api` object:

```ts
createTenant(data: CreateTenantRequest)
  → postApi<CreateTenantRequest, TenantSummary>("/tenants", data)

createVendor(data: CreateVendorRequest)
  → postApi<CreateVendorRequest, VendorSummary>("/vendors", data)

createCategory(data: CreateCategoryRequest)
  → postApi<CreateCategoryRequest, CategorySummary>("/categories", data)

createProduct(data: CreateProductRequest)
  → postApi<CreateProductRequest, ProductSummary>("/products", data)
```

Response type matches what the backend controller actually returns:
`TenantSummary`/`VendorSummary`/`CategorySummary`/`ProductSummary` (the
existing `*Summary` types in `api.ts`), so the new methods compose with
all existing read consumers without new types.

Existing 11 GET methods, `fetchApi`, `buildQueryString`, `API_BASE_URL`,
and the import block are byte-identical to the pre-P7-009 state — no
existing frontend screen or component is affected.

## DESIGN PRINCIPLES

1. UUID primary keys
2. createdAt + updatedAt on all tables
3. Soft delete where appropriate
4. tenantId on all business tables
5. Audit logging for important changes
6. Decimal(19,4) for money (no money logic)
7. No cross-tenant data leakage
8. No destructive migration
9. No seed/reset/init scripts
10. No production database connection
11. No auth/payment business logic
12. Modular SaaS architecture support

## TENANT ISOLATION RULES

- Tenant is top-level isolation boundary
- Vendor, Category, Product carry tenantId
- User is global (platform-level)
- Membership bridges User ↔ Tenant
- All business queries filter by tenantId
- Slug uniqueness scoped to tenant (Category, Product)
- Cross-tenant access requires Owner/Admin authorization (audit-logged)

## AUDITLOG DESIGN

- id, tenantId (optional), actorUserId (optional), action, entityType, entityId, summary, metadata (JSONB), createdAt
- Immutable: no soft delete, no updates, no deletes
- Action naming: ENTITY_ACTION (e.g., TENANT_CREATED)

## SOFT DELETE DESIGN

- Tenant: deletedAt nullable
- User: deletedAt nullable
- Membership: no soft delete (use status field)
- Vendor: deletedAt nullable
- Category: deletedAt nullable
- Product: deletedAt nullable
- AuditLog: no soft delete (immutable)

## STATUS/ENUMS DESIGN

- TenantType: PLATFORM, VENDOR
- TenantStatus: ACTIVE, SUSPENDED
- UserStatus: ACTIVE, DISABLED
- MembershipStatus: ACTIVE, INVITED, SUSPENDED
- VendorStatus: DRAFT, ACTIVE, SUSPENDED
- CategoryStatus: ACTIVE, HIDDEN
- ProductStatus: DRAFT, ACTIVE, ARCHIVED
